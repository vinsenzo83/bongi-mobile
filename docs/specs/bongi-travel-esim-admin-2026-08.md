# 봉이 여행 eSIM 어드민 설계서 (CMI API V4.1 기반)

2026-08-14 · 봉이랩스
선행 문서 — `bongi-travel-esim-2026-07.md`(기획), `CMI_API명세서_V4.1_전체한글번역`(API), `Standardized GDS Cooperation Agreement`(계약)

> **2026-07 기획서 대비 가장 큰 변경**: CMI `createOrder`는 **`ICCID`가 필수 파라미터**이고 `includeCard`는 **고정값 0**(카드 미포함, 패키지만 주문)입니다.
> 즉 **eSIM 프로파일과 요금제가 분리**되어 있어, 주문 시점에 **대상 ICCID가 이미 존재**해야 합니다.
>
> **다만 이것은 "재고 선매입"이 아닙니다.** `CMI_Distribution_Blank_eSIM_기술명세서 v1.0`(2026-08-10, CMI 담당자 확인)에 따르면 — **① Distribution Standard eSIM은 무료**, **② 재고 선매입 불필요**(Balance 선입금 후 주문 시 공급가 차감), **③ 동일 ICCID에 국가를 바꿔가며 반복 주문 가능**.
> → 관리 대상은 창고 재고가 아니라 **고객·단말에 매핑된 eSIM 프로파일**입니다.

## 0. 멀티 공급사 아키텍처 (전제)

**공급처를 2곳 운영합니다.**

| | 관계 | 성격 |
|---|---|---|
| **① CMI** | **본사 직거래** (Distribution) | 고정 카탈로그 600여 종. 12개월 $64,000 약정 |
| **② A2Z 거래처** | **CMI에서 공급받는 파트너** (Pay-As-You-Go) | **커스텀 설계권 보유** — CMI 고정 카탈로그에 없는 SKU를 만들 수 있음 |

> **근본이 같은 물건입니다.** 둘 다 CMI 로밍망이고, 상품 구조(`Unlimited (X/day high speed)`)·저속 정책·UPCC 과금·미활성 취소 규칙·365일 활성화 기한이 **동일**합니다.
> → **사양 등가성 검증 부담이 거의 없습니다.** 확인할 것은 **거래처가 덧씌우는 자체 정책**(취소 수수료·기한 단축·정산 주기)과 **커스텀 SKU의 사양**뿐입니다.

##### 두 공급처는 경쟁이 아니라 보완 관계

```
CMI에 있는 SKU   → CMI 직거래   (중간마진이 없어 구조적으로 더 쌈 + 약정 소진)
CMI에 없는 SKU   → A2Z 거래처   (결품 해소)
```

**A2Z 거래처가 우리 결품을 정확히 메웁니다.**

| 우리 결품 | 비고 |
|---|---|
| **완전 무제한** | 커스텀 설계 영역. 유심사·도깨비가 이 경로로 판매 |
| **4GB · 5GB 고속 티어** | 우리 상한은 3GB |
| **일본 500MB** | 유심사가 CMI-DW로 30개 판매 중 |
| **중국 단독** | CMI 고정 카탈로그에 0건 |
| **괌 · 사이판** | 글로벌 다지역 팩으로만 커버(1GB 3일 11,606원) |

운용 방식은 **SKU 단위 최저가 자동 선택**이되, 위 구조상 겹치는 구간은 대부분 CMI가 선택됩니다.

이 전제 때문에 설계 전반이 달라집니다. 나중에 붙이면 스키마를 갈아엎어야 하므로 **처음부터 N개 공급사**를 가정합니다.

### 0.1 최저가 자동 선택의 전제조건 — 사양 등가성

> **같은 물건일 때만 가격 비교가 성립합니다.**
> eSIM Story 단가표를 CMI와 나란히 놓았다가, Story는 `Country · Days · Data · Price` 네 열뿐이고 **"일 X 고속 후 저속 무제한"인지 "일 X 쓰고 종료"인지 표기가 없어** 비교 자체가 무효였던 사례가 있습니다.

그래서 SKU를 공급사에 연결할 때 **등가성 항목을 명시적으로 입력·승인**해야 하고, **승인 전에는 라우팅 후보에서 제외**됩니다.

| 등가성 항목 | 확인 내용 |
|---|---|
| **과금 구조** | 일 단위 고속 + 저속 무제한 / 정량 총량 / 고속 소진 후 차단 |
| **고속 제공량** | 500MB · 1GB · 2GB · 3GB … (일 단위인지 총량인지) |
| **저속 속도** | kbps 값. 미공개면 "미확인"으로 표기 |
| **커버리지** | 포함 국가 목록 (예: 유럽 42 vs 44는 다른 상품) |
| **망 종류** | 로밍망 / 로컬망 |
| **테더링** | 핫스팟 지원 여부 |
| **부가 혜택** | 제로레이팅(구글맵·ChatGPT) 등 |

**등가성 등급**

| 등급 | 의미 | 라우팅 |
|---|---|---|
| `identical` | 사양 동일 확인 | **최저가 비교 대상** |
| `equivalent` | 실질 동등(커버리지 ±소수국 등) | 비교 대상, 화면에 차이 표기 |
| `different` | 사양 다름 | **비교 제외.** 별도 SKU로 분리 |
| `unknown` | 미확인 | **판매 중단.** 확인 전까지 라우팅 금지 |

### 0.2 라우팅 정책

주문 시점에 `esim_sku_supply`(SKU × 공급사) 중에서 고릅니다.

```
후보 = 해당 SKU의 공급사 중
       equivalence ∈ {identical, equivalent}
       AND 공급사 상태 = 정상
       AND 재고/발급 가능

[1순위] 보유 여부      후보가 1곳뿐이면 → 그곳으로 확정
[2순위] CMI 우선       후보가 2곳 이상이고 원가 갭 ≤ τ 이면 → CMI
[3순위] 최저가         갭 > τ 이면 → 싼 쪽

발급 = 1순위 시도 → 실패 시 다음 후보로 자동 전환(폴백)
```

> **★계약 확정: Option 2 ($12,800 일시선납·무약정)**
> 아래 약정 연동 로직은 **Option 1을 택했을 때의 설계**입니다. Option 2에서는 **`commitment_mode = 'option2'`로 대부분 비활성**됩니다. 2년차에 Option 1이나 PAYG로 올릴 경우를 대비해 구조는 남겨둡니다.
>
> | 항목 | Option 2 적용 |
> |---|---|
> | 약정 미달 추가청구 로직 | **OFF** (미달 청구 없음) |
> | 마진율 페이스 연동 | **OFF** — 기본 40% 고정 |
> | 라우팅 τ 페이스 연동 | **완화** — 3% 고정 |
> | **선납 잔액 소진 관리** | **ON** — 미소진분은 소멸(환불 불가)이므로 여전히 관리 필요 |
>
> **Option 2 목표치** — $12,800 = **1,834만원**, 12개월 균등 소진 시 **월 153만원 = 월 420건 = 부착률 4.2% = 하루 14건**(직영점 13곳이면 매장당 하루 1건).
> **미소진 리스크 상한 1,834만원** (Option 1은 미달 시 최대 9,170만원 추가청구).

#### 왜 갭이 작으면 CMI인가 — 약정 소진 논리 *(Option 1 전용)*

CMI **Distribution Option 1**은 12개월 **USD 64,000 최소 매입 약정**이고, 미달 시 **차액을 그대로 청구**받습니다(계약 7.2).

> 소진하지 못한 약정은 **돈만 내고 물건은 못 받는 순손실**입니다.
> 반대로 약정 범위 안에서의 CMI 매입은 **어차피 낼 돈을 상품으로 바꾸는 것**이라, **실질 한계원가가 0에 가깝습니다.**

그래서 "2차 공급사가 100원 싸다"는 이유로 물량을 빼면, **그 100원을 아끼려다 약정 미달분을 통째로 물어내는** 결과가 됩니다.

**추가로 주의** — 고객이 **CMI 공식 사이트에서 직접 산 추가충전은 우리 실적에 안 잡힙니다**(계약 7.3). 약정 진척 계산에서 제외해야 합니다.

#### 갭 임계값 τ — 약정 진척에 연동

τ를 고정값으로 두면 안 됩니다. **약정을 잘 소진하고 있으면 좁히고, 뒤처지면 넓혀야** 합니다.

```
소진 페이스 = 누적 CMI 매입액 ÷ (약정액 × 경과월 ÷ 12)

페이스 ≥ 1.0   (정상·초과)  →  τ = τ_min      (기본 3%)
페이스 < 1.0   (미달)       →  τ = τ_min + (1 − 페이스) × (τ_max − τ_min)
잔여 3개월 미만 & 페이스 < 0.8 →  τ = ∞        (무조건 CMI)
```

**예시** — τ_min 3%, τ_max 30%

| 소진 페이스 | τ | 해석 |
|---|---|---|
| 1.10 (초과) | **3%** | 여유 있음 → 3% 넘게 싸면 2차로 |
| 0.85 | **7.5%** | 조금 뒤처짐 → CMI 쪽으로 더 붙임 |
| 0.60 | **13.8%** | 많이 뒤처짐 → 웬만하면 CMI |
| 0.60 & 잔여 2개월 | **∞** | **전량 CMI** — 미달 차액이 더 비쌈 |

τ_min·τ_max·잔여기간 기준은 **`esim_policies`에서 조정**합니다(하드코딩 금지).

> **Option 2(무약정 선납 $12,800)로 계약하면** 이 로직은 필요 없습니다. 약정이 없으니 순수 최저가로 가면 됩니다. **정책 테이블의 `commitment_mode` 값으로 on/off** 합니다.

**폴백은 최저가 정책과 별개로 반드시 필요합니다.** 최저가 공급사가 발급 실패했을 때 주문을 살리려면 다음 후보로 넘어가야 합니다. 로밍도깨비가 "대체상품 32개"를 운영하는 것과 같은 구조입니다.

**라우팅 결과는 주문에 반드시 기록**합니다 — 어느 공급사로 나갔는지 모르면 CS·정산·장애대응이 전부 막힙니다.

### 0.2.1 자동 / 수동 전환 — 3단계 오버라이드

**전부 자동이면 안 됩니다.** 특정 목적지는 망 품질 때문에 공급사를 고정해야 하고, 신규 공급사는 검증 기간 동안 수동으로 묶어둬야 합니다.

우선순위는 **좁은 범위가 이깁니다.**

```
① SKU 설정        ← 가장 우선
② 목적지 설정
③ 전역 기본값     ← 최후
```

**각 단계에서 고를 수 있는 값**

| 모드 | 동작 |
|---|---|
| `auto` | **원가 최저 공급사 자동 선택** (기본값) |
| `manual` | **지정 공급사로 고정.** 그 공급사가 실패해도 다른 곳으로 안 넘김 |
| `manual_fallback` | 지정 공급사 우선, **실패 시에만** 다음 후보로 폴백 |
| `off` | 판매 중단 |

> 실무 권장은 **전역 `auto` + 검증 안 끝난 공급사·민감 목적지만 `manual`**입니다.
> `manual`은 폴백을 막으므로 **발급 실패가 곧 주문 실패**가 됩니다. 대부분은 `manual_fallback`이 안전합니다.

**어드민 화면** — SKU 목록에 `모드` 컬럼과 배지(`자동` / `수동:CMI` / `수동+폴백`), 목적지 단위 일괄 변경, **오버라이드가 걸린 SKU만 필터**. 어느 단계에서 온 설정인지(상속/직접지정)도 표시합니다.

**변경 이력 기록** — 누가 언제 어느 SKU를 수동으로 바꿨는지 남깁니다. 원가가 비싼 쪽으로 고정한 게 방치되면 마진이 새는데, 이력이 없으면 못 찾습니다.

### 0.2.2 공급사별 커버리지 차이 — 있는 곳과 없는 곳

**모든 공급사가 모든 상품을 갖고 있지 않습니다.** CMI만 있는 것, 2차 공급사만 있는 것, 둘 다 있는 것이 섞입니다.

| SKU 상태 | 처리 |
|---|---|
| **양쪽 보유** | 최저가 자동 선택. **폴백 가능** |
| **CMI 단독** | CMI로 발급. **폴백 없음** → 장애 시 판매 중단 |
| **2차 단독** | 2차로 발급. **폴백 없음** |
| **양쪽 없음** | 진열 불가 — **결품 목록**으로 관리 |

**단독 공급 SKU는 별도로 표시해야 합니다.** 폴백이 없다는 뜻이라, 그 공급사에 장애가 나면 해당 상품이 그대로 죽습니다. 대시보드 경보 대상입니다.

#### 커버리지 매트릭스 화면 (신규)

행=진열 SKU(목적지 × 고속량 × 일수), 열=공급사. 셀에 **원가 + 등가성 등급 + 채택 여부**를 표시합니다.

```
                    CMI          공급사B       채택      모드
일본 1GB 3일        2,622 ✓id    2,410 ✓id     공급사B   자동
일본 500MB 1일      —            845  ⚠unknown  —        중단   ← 등가성 미확인
대만 1GB 4일        —            3,955 ✓eq      공급사B   자동   ← CMI 단독 결번
홍콩·마카오 1GB 3일  1,934 ✓id    —             CMI      자동   ← CMI 단독(폴백 없음)
```

**필터** — 단독 공급만 / 등가성 미확인만 / 수동 고정만 / 결품만 / **원가 역전(비싼 쪽으로 고정된 것)**

> 이 화면 하나로 **어디에 구멍이 있고, 어디서 마진이 새고, 어디가 장애에 취약한지**가 한눈에 보여야 합니다.

### 0.3 공급사별로 다른 것

| 항목 | CMI | 2차 공급사 |
|---|---|---|
| **인증** | WSSE (`Base64(SHA256(Nonce+Created+Password))`), 토큰 10분 | 공급사별 상이 |
| **재고 모델** | **ICCID 풀 선보유 필수** (`createOrder`에 ICCID 필수) | 주문 시 발급형일 수 있음 |
| **정산** | **선불 충전 차감** (잔액 부족 시 즉시 정지) | 후불·월정산일 수 있음 |
| **약정** | 12개월 $64,000 (Option 1) | 상이 |
| **알림** | 웹훅 3종 (개통·사용·eSIM상태) | 상이 |
| **성공코드** | 대부분 `0`, 해지는 `0000000` | 상이 |

→ **어댑터는 포트-어댑터 패턴**으로, 공통 인터페이스를 두고 공급사별 구현을 갈아끼웁니다.

### 0.4 공통 어댑터 인터페이스

```js
// server/services/esim/ports.js — 모든 공급사가 이 계약을 구현
{
  id, name,                       // 'cmi' | 'xxx'
  capabilities: {                 // 지원 기능 선언
    needsCardPool,                // ICCID 선보유 필요 여부
    supportsEarlyEnd,             // 조기 종료
    supportsRefuel,               // 추가충전
    supportsUsageQuery,           // 사용량 조회
    webhooks: []                  // 제공하는 알림 종류
  },
  listPackages(),                 // 카탈로그 동기화
  quote(sku),                     // 원가(현지통화 → KRW)
  issue(order),                   // 발급 → { providerOrderId, iccid, activationCode, smdpAddress }
  cancel(order),                  // 해지·조기종료
  usage(ref),                     // 사용량
  cardStatus(iccid),              // 카드 상태 (needsCardPool인 경우)
  verifyWebhook(req)              // 알림 서명 검증
}
```

**어드민은 `capabilities`를 읽어 화면을 조립합니다.** 예를 들어 `needsCardPool=false`인 공급사는 재고 화면에 안 나오고, `supportsRefuel=false`면 그 SKU에 충전 버튼이 안 뜹니다.

## 0.5 판매 채널 구조

| 순위 | 채널 | 역할 | 수수료 |
|---|---|---|---|
| **1** | **네이버 스마트스토어** | **신규 유입** — 검색 노출·결제 신뢰 | 네이버 수수료 (확인 필요) |
| **2** | **자체 앱** | **교환·재구매** — 수수료 없음, 고객 데이터 확보 | PG 수수료만 |
| — | **직영점 13곳** | **앱 설치 + eSIM 선설치** — 앱 채널의 공급원. CAC 0 | 없음 |

> **매장은 별도 판매 채널이 아니라 앱 채널의 유입원**입니다. 휴대폰 판매 시 앱 설치 + Blank eSIM 선설치를 해두면, 그 고객은 여행 때마다 앱에서 구매합니다.

### 0.5.1 발급·발송 방식 — **직접 발급 + 카카오 알림톡·이메일 즉시 발송**

주문이 들어오면 **우리가 프로파일을 발급해 고객에게 바로 보냅니다.** 앱 설치를 강제하지 않습니다.

```
① 스마트스토어 주문 (네이버 커머스API로 수집)  /  앱·매장 주문
② 결제 확인
③ ICCID 배정 → 공급사 Package Order
④ 3.2.13으로 activationCode + smdpAddress 수신
⑤ 설치 페이지 생성 (QR + 수동입력값 + OS별 가이드)
⑥ ★카카오 알림톡 + 이메일 동시 발송
      알림톡 실패 → LMS 자동 대체발송
```

#### 발송 설계

**QR 이미지를 직접 보내지 말고 「설치 페이지 링크」를 보냅니다.**

| | 이유 |
|---|---|
| 카카오톡·이메일에서 **이미지가 유실·압축**되면 QR 인식이 안 됩니다 | 링크는 안 깨짐 |
| **수동 입력값**(SM-DP+ 주소·활성화 코드)을 함께 줘야 합니다 | QR 스캔 실패 시 유일한 대안 |
| **OS별 설치 가이드**가 화면 안에 있어야 합니다 | iOS·Android 절차가 다름 |
| **재열람·재발송**이 가능해야 합니다 | 고객이 메시지를 지워도 링크로 복구 |
| 설치 여부·잔여 데이터를 **같은 페이지에서** 보여줄 수 있습니다 | 3.2.17 웹훅·3.2.8 연동 |

→ 설치 페이지는 **주문별 고유 토큰 URL**로 생성하고, **유효기간과 접근 제한**을 겁니다.

#### 알림톡 운영

- **템플릿 사전 승인**이 필요합니다 — 발급 완료 / 만료 D-30·D-7·D-1 / 재발송 / 취소 완료 등 **유형별로 미리 등록**
- **실패 시 LMS 대체발송** 필수 — 카카오 미가입·수신거부 대응
- **발송 이력 저장** — 만료 안내 고지 이행 증거로도 쓰입니다(약관 방어 장치 2번)

#### 스마트스토어 상품 등록

목적지별 상품 + **옵션 조합**으로 처리합니다.

```
상품: "일본 여행 eSIM"
  옵션1 고속량: 500MB / 1GB / 2GB / 3GB
  옵션2 일수:   1~30일
  → 목적지당 최대 120조합, 목적지 25개
```

- 상품 유형은 **디지털 콘텐츠(e쿠폰)** 계열로 등록 — 실물 배송이 아님
- **청약철회 제한 고지**를 상품 상세에 명시(활성화 후 환불 불가·180일 유효기간)
- 주문 수집 → 발급 → 발송 → **발송완료 처리**까지 커머스API로 자동화

### 0.5.2 채널별 가격 — **단일 가격** 원칙

수수료 차이가 작아 채널별 가격 분리는 실익이 없습니다.

| 채널 | 수수료 | 건당 실이익 | 실마진 |
|---|---|---|---|
| 자체 앱 | 2.5%(PG) | 2,276원 | **37.5%** |
| 스마트스토어 | 5.6%(가정) | 2,088원 | **34.4%** |

### 2.2 상품 관리 (P0)

#### (a) 패키지 동기화 — `3.2.2 app_getDataBundle_SBO`

`cooperationMode`(**필수**, 우리 값 확인 필요) 지정 후 전량 pull → `esim_packages`에 upsert.

동기화 시 반드시 화면에 표시할 것:

#### (b) 가격 정책

`feedback_no_hardcode` 준수 — 하드코딩 금지, 정책 테이블에서 읽습니다.

```
소매가 = 도매USD × 환율 × (1 + 조달부대비) ÷ (1 − 마진율)
       → 100원 단위 절삭
```

**정책 테이블에 둘 값** — 환율(수동/자동), 조달부대비(기본 1.5%), **목적지별·기간구간별 마진율**, 100원 절삭 규칙, 최저 판매가 하한

**가격 결정권은 우리에게 있습니다.** 계약서에 `the Partner shall have the right to decide the retail price of the Products in the Territory`로 명시돼 있고, CMI 구두 확인도 동일합니다.

다만 단서가 둘 붙습니다.

| 단서 | 내용 |
|---|---|
| **덤핑 금지** | 악의적 할인 등 **시장 교란·불공정 경쟁을 일으킨다고 CMI가 판단하는** 가격 설정 금지. 판단 주체가 CMI 재량 |
| **최저가 하한** | **CMI가 지정한 최저가(designated minimum price) 미만 판매 금지.** 위반 시 계약 해지 + 손해배상액 CMI 재량 산정 |

> **하한은 CMI가 값을 지정했을 때만 성립**합니다. 현재 "자유롭게 책정" 안내를 받았으므로 **지정값이 없는 상태로 보입니다.**
> → 어드민은 `cmi_min_price`를 **nullable 경고 필드**로 둡니다. 값이 **없으면 제한 없이 저장**하고, CMI가 나중에 지정하면 그때 하한 검증을 켭니다. 저장을 막는 하드 블록은 두지 않습니다.
> → 다만 **"현재 지정 최저가 없음, 설정 시 사전 통지" 확인을 서면으로 받아두는 것**을 권합니다. 페널티가 계약 해지 수준이라 구두만으로는 위험합니다.

#### (c) 진열 관리 — 커버리지 재조합

CMI 카탈로그를 그대로 노출하면 안 됩니다. **판매 목적지 ≠ CMI 패키지**입니다.

| 판매 목적지 | 배정 CMI 패키지 | 비고 |
|---|---|---|
| 중국 | **중국+베트남** | 전 일수 최저가 |
| 홍콩 / 마카오 / 홍콩·마카오 | **홍콩·마카오** | 8/17 단독 단종 |
| 대만 | **대만**(3·5·7·10일) + **대중화권**(그 외) | 일수별로 다른 패키지 |

→ `esim_display_products`(고객에게 보이는 상품) ↔ `esim_packages`(CMI 원본)를 **1:N 매핑**하고, **(용량, 일수)별로 어떤 패키지를 쓸지 지정**하는 매핑 테이블이 필요합니다.

### 2.3 eSIM 프로파일 관리 (P0) ★신규

**창고 재고가 아니라 「고객 × 단말 × ICCID」 매핑 관리**입니다. Standard eSIM이 무료이고 선매입이 없어 재고 리스크는 없습니다.

#### 두 가지 발급 경로

| 경로 | 시점 | 설명 |
|---|---|---|
| **선설치** | **휴대폰 판매 시** | 직영점에서 단말에 Blank eSIM을 미리 설치. **봉이만의 무기** — 여행 시 QR 없이 앱에서 구매만 하면 됨 |
| 온라인 | 여행상품 구매 시 | 그 자리에서 Blank eSIM 발급 → QR 전달 |

#### ★ 3개 타이머를 반드시 분리 관리

> 하나의 `expiry` 필드로 합치면 안 됩니다. **서로 다른 3개의 시계**입니다.

| 타이머 | 기간 | 시작·갱신 |
|---|---|---|
| **`profile_expired_at`** | **2년** | CMI 발급 시점부터. **새 상품을 주문할 때마다 그 시점 기준 2년으로 리셋** |
| **`activation_deadline`** | **주문 후 365일** | 이 기간 내 현지 활성화 필수. 미활성 시 상품 소멸 |
| **`usage_expired_at`** | 상품 기간(3·5·7일…) | **현지망 활성화 시점부터** 카운트. 주문일 아님 |

**예시** — "일본 5일"을 3월에 주문하면 5일은 3월부터가 아니라 **일본에 도착해 접속한 순간부터** 5일입니다. 단 **365일 안에 활성화**해야 합니다.

> **계산 규칙 주의** — 서버에서 `365 × 24시간`을 단순 가산하면 CMI 규칙과 어긋날 수 있습니다. **CMI가 반환하는 만료 Timestamp가 있으면 그 값을 저장**합니다.

#### 상태 모델

**Profile** — `ISSUED`(발급·미설치) → `INSTALLED`(단말 설치) → `ACTIVE`(상품 보유) → `DELETED`(고객 삭제) / `EXPIRED`(2년 만료)

**Package** — `ORDERED`(주문·미활성) → `ACTIVATED`(현지 활성) → `COMPLETED`(사용 종료) / `CANCELLED`(미활성 취소) / `EXPIRED`(365일 미활성)

#### 프로파일 삭제·재발급

고객이 단말에서 프로파일을 지우면 **같은 프로파일은 재설치할 수 없습니다.** **새 eSIM을 발급**해야 하고, 기존 레코드는 `DELETED`로 보존한 뒤 `replacement_iccid`로 연결합니다.

> 고객 UI에 **"여행용 eSIM — 삭제하지 마세요"** 안내가 필수입니다. 삭제가 곧 재발급 비용·CS 부담입니다.

#### 어드민 화면

- **프로파일 목록** — 고객·단말·ICCID·상태·`profile_expired_at`·마지막 주문일
- **만료 임박** — 2년 만료 D-60/D-30. 상품 주문 시 리셋되므로 **재구매 유도 타깃**
- **미활성 상품** — `activation_deadline` 임박 건. **365일 소멸 전 안내 발송**
- **삭제·재발급 이력** — 사유·횟수. `installCount`(3.2.13)와 대조
- **CMI 대사** — 내부 상태 ↔ CMI 상태 불일치 탐지·수동 복구

### 2.7 결제 취소 · 환불 (P0으로 상향)

> **P1에서 P0으로 올립니다.** 발급 실패 시 결제 자동취소가 없으면 **돈은 받고 상품은 없는 상태**가 그대로 남습니다.

#### (a) CMI 회수 가능 범위 — 규정의 출발점

오류코드가 해지 조건을 규정합니다.

| 코드 | 내용 |
|---|---|
| `1000035` | **주문 시점이 당월이 아니면 해지 불가** |
| `1000044` | **개통 대기 상태가 아니면 해지 실패** |
| `1000043` | 일부 패키지가 이미 개통됨 — 처리 실패 |
| `1000041` | 완료 상태만 해지 가능 |
| `1000030` | 일부 해지 실패 또는 해지 가능 잔액 부족 |
| `1000047` | 환불 실패 |

#### 회수 조건 — 미활성이면 365일 내 언제든 100%

**CMI 확인 완료.** 미만료·미활성 상품은 **활성화 기한(365일) 안에서 언제든 취소**할 수 있고, **상품 금액은 CMI Balance로 전액 롤백**됩니다.

> 未过期未激活的套餐**可以随时取消**，套餐金额回滚至账号
> — CMI 담당자 답변 (`Blank eSIM 기술명세서 v1.0` 부록 A)

**즉 회수 가능 여부를 가르는 기준은 「월(月)」이 아니라 「활성화 여부」입니다.**

| 구분 | 회수 |
|---|---|
| **미활성 · 365일 이내** | **100% Balance 롤백** |
| 활성화 후 | 불가 |
| 365일 미활성 소멸 | 불가 |

**이게 우리 환불 정책의 최대 무기입니다.** 고객이 사기만 하고 안 썼다면 **1년 안에는 언제 환불 요청해도 원가 손실이 0**입니다. 경쟁사보다 관대한 규정을 손실 없이 걸 수 있습니다.

> **다만 API 오류코드 `1000035`**(주문 시점이 당월이 아니면 해지 불가)가 명세서에 존재합니다. **어느 인터페이스에 걸리는 제약인지 확인이 필요**합니다 — `3.2.12 채널 해지`(정산 롤백)와 `3.2.9 패키지 조기 종료`는 성격이 다르므로, 미활성 취소에 쓰는 경로가 무엇인지 CMI에 명시적으로 받아둡니다.
> 운영상으로는 **`1000035`가 반환되면 자동 재시도하지 않고 수동 처리 큐로** 넘깁니다.

#### (b) 주문 생애주기와 환불 가능 구간

**프로파일 단계와 패키지 단계는 별개입니다.** 돈이 나가는 것은 패키지 주문이고, 프로파일 발급·설치에는 상품이 붙지 않습니다.

```
[프로파일]  PROFILE_ISSUED ─ CMI가 Blank eSIM 생성, ICCID만 존재   (원가 0, Standard eSIM 무료)
            PROFILE_INSTALLED ─ 고객 단말에 설치. 한국에서 이뤄짐   (여전히 상품 없음)

[패키지]    결제완료 ─ CMI 주문 전                    → 전액 환불 (원가 미발생)
            PKG_ORDERED ─ 주문 성공, Balance 차감      → ★취소 시 100% 롤백
            PKG_ACTIVATED ─ 현지망 첫 접속, 사용 시작  → 회수 불가
            PKG_COMPLETED / PKG_EXPIRED               → 회수 불가
```

**돈이 나가는 시점은 `PKG_ORDERED`, 취소가 막히는 시점은 `PKG_ACTIVATED`입니다.** 그 사이가 **100% 환불 구간**이고 최대 **365일**입니다.

> **설치(`PROFILE_INSTALLED`)와 활성화(`PKG_ACTIVATED`)는 다릅니다.**
> 한국에서 프로파일을 깔아놨어도 **목적지 현지망에서 데이터를 켜기 전까지는 미활성**입니다.
> → 선설치 모델에서 휴대폰 구매 시 여행상품을 미리 팔아도, **출국 전까지는 계속 미활성이라 언제든 100% 환불**됩니다. **판매 저항이 거의 없습니다.**
>
> 웹훅 `3.2.17`(프로파일 설치 단계)과 `3.2.15`(패키지 개통)를 **분리 저장**해야 이 구분이 성립합니다. 하나로 합치면 환불 판정이 무너집니다.

#### (b-2) ★봉이 자체 규정 — 사용기한 180일

**고객에게 부여하는 사용기한은 180일입니다.** CMI 활성화 기한은 365일, A2Z 거래처는 180일로 예상됩니다.

```
[CMI 소싱]   구매 ──── 180일 ──────────────── 365일
                        └ 봉이 만료          └ CMI 회수 마감   버퍼 185일 ✅

[A2Z 소싱]   구매 ──── 180일 ──── 180일
                        └ 봉이 만료 = 회수 마감              버퍼 0일 ❌
```

##### ★공급사별 회수 마감이 다릅니다

**A2Z 거래처는 CMI처럼 365일을 못 받습니다.** 그쪽도 우리에게 180일을 적용할 가능성이 높습니다.
→ 고객 기한과 회수 마감이 **같은 날**이 되어, 만료 배치가 하루만 밀리거나 고객이 179일차에 요청하면 **원가를 통째로 날립니다.**

**계산식**

```
고객 사용기한 = min( customer_use_days,  공급사 회수마감 − safety_buffer_days )
```

| 소싱 | 공급사 마감 | 고객 기한 | 버퍼 |
|---|---|---|---|
| **CMI** | 365일 | 180일 | **185일** |
| **A2Z 거래처** | 180일(예상) | **180일** | **0일 → 운영으로 보완** |

##### 채택 — 전 상품 180일 통일, 버퍼는 운영으로 확보

**고객 유효기간은 180일로 확정합니다.** 업계 표준(유심사 180일)과 동일하고, 공급사에 따라 다르게 고지할 수 없기 때문입니다.

문제는 A2Z 소싱분의 버퍼가 0이라는 점인데, **기한을 줄이는 대신 아래 4중 장치로 메꿉니다.**

| # | 장치 | 효과 |
|---|---|---|
| **1** | **취소 요청 접수 마감 D-7 약관 명시** — "만료 7일 전까지 취소 요청" | **처리 여유 7일 확보.** 가장 확실한 장치 |
| **2** | **만료 배치를 만료일 당일 00:30 KST 자동 실행** + 실패 시 30분 간격 재시도 3회 + 실패 알림 | 만료 당일 안에 회수 완료 |
| **3** | **A2Z 계약 시 회수 마감을 고객 기한보다 길게 요구** (최소 **+14일**) | 근본 해결. 협상 항목으로 명시 |
| **4** | **D-30 / D-7 / D-1 미활성 안내** | 만료 전 고객이 스스로 취소하도록 유도 |

> **1번이 핵심입니다.** 고객 유효기간(180일)과 취소 접수 마감(173일)을 분리하면, 공급사 마감이 180일이어도 처리 여유가 7일 생깁니다. **약관에 명시만 하면 되는 무비용 장치**입니다.

> **시간대 주의** — 공급사 마감은 **UTC 기준**일 수 있습니다. KST가 9시간 앞서므로, 우리 기준 만료일 당일에 이미 UTC로는 마감이 지났을 수 있습니다. **배치는 UTC 기준으로 여유를 두고** 실행합니다.

**어드민 검증** — SKU에 공급사를 연결할 때 `공급사 회수마감 < 고객기한 + 최소여유(7일)`이면 **경고를 띄웁니다.** 저장은 허용하되 **위험 SKU 목록**에 올려 상시 노출합니다.

**① 업계 관행 범위 안이고, 오히려 관대한 쪽입니다.** 국내 eSIM 사업자의 상품 유효기간은 **90~180일**대로 형성돼 있습니다. 유심사 상품 약관에는 **`상품 유효 기간: 180일`**이 명시돼 있고(공개 API 플랜 설명, 2026-08 수집), **90일짜리를 쓰는 곳도 있습니다.**

→ 우리가 **상한선인 180일**을 택하면, 관행보다 짧게 잡아 불리하게 만든 게 아니라 **가장 여유 있는 축**에 서게 됩니다. "부당하게 불리한 조항"이라는 주장이 성립하기 어렵습니다.

**② 안전버퍼가 필요합니다.** 공급사 회수 마감에 딱 붙여 놓으면 만료 배치가 하루만 밀려도 **원가를 통째로 날립니다.** 아래 계산식으로 버퍼를 강제합니다.

#### 180일 경과 처리 — 자동 소멸

| 주체 | 처리 |
|---|---|
| **고객** | 상품 소멸. **환불 없음** |
| **CMI** | 만료 시점에 미활성 상품 **취소 → 원가 100% 회수** |
| **손익** | **소매가 전액이 순이익** (마진 100%) |

> **법무 검토는 여전히 필요합니다.** 약관규제법상 유효기간 경과 시 전액 몰취 조항은 다툼의 여지가 있습니다. 다만 **업계 표준(유심사 180일)과 동일**하다는 점이 방어의 핵심 근거가 됩니다. 아래 3중 장치를 함께 구현해 리스크를 더 낮춥니다.

**방어 장치 3종 (필수 구현)**

| # | 장치 | 목적 |
|---|---|---|
| **1** | **구매 화면 사전 고지 + 동의 체크박스** — "구매일로부터 **180일** 내 미사용 시 자동 소멸되며 환불되지 않습니다" | 고지 없는 제한은 무효가 되기 쉬움. **1순위** |
| **2** | **D-30 / D-7 / D-1 만료 안내 발송** (앱푸시·문자·이메일) | 고지 의무 이행 **증거 확보**. 발송 이력을 보관 |
| **3** | **만료 후 연장 요청 창구 유지** — 고객이 요청하면 연장 승인(먼저 안내하지는 않음) | **전액 몰취 조항이 아니게 됨.** CMI 365일까지 여유가 있어 연장해도 손실 없음 |

> **규모 전망 — 소멸 수익은 사업 항목이 아닙니다.**
> 여행 eSIM은 **구매 시점이 출국 직전**이라 미사용률이 구조적으로 낮습니다. 상품권처럼 사놓고 잊는 물건이 아닙니다.
> → 이 규정의 실익은 **수익이 아니라 ① 원가 회수 마감선 관리 ② CS 응대 기준**입니다. 소멸 수익 집계·회계 처리는 **P2로 후순위**, **만료 배치와 회수 로직은 P1**로 유지합니다.
>
> **단, 선설치 모델에서 "휴대폰 구매 시 여행상품 선판매"를 밀면 미사용률이 올라갑니다.** 구매–여행 간격이 벌어지기 때문입니다. 그 전략을 채택하면 이 규정이 실제로 작동하기 시작하므로, **미사용률을 지표로 추적**합니다.

**어드민 구현**
- `customer_use_deadline` = `ordered_at + 180일` (`customer_use_days = 180`)
- `cancel_request_deadline` = `customer_use_deadline − 7일` ← **취소 요청 접수 마감**
  - 공급사별 `supplier_cancel_deadline_days` — CMI 365, A2Z 180(확인 필요)
  - **SKU 저장 시 여유 검증** — `공급사마감 < 고객기한 + 7일`이면 경고 + 위험 SKU 등재
  - 업계 관행 **90~180일** 범위. 우리는 상한인 180일 채택
- 만료 배치 — 기한 경과 미활성 건을 **CMI 취소 → 원가 회수 → 상태 `EXPIRED_FORFEITED`**
- **소멸 수익 집계**(P2) — 월별 소멸 건수·금액. 회계 처리 기준 확인 필요
- **미사용률 추적**(P1) — 판매 채널별(온라인 / 매장 선판매) 미사용 비율. 선판매 전략의 실효성 판단 지표
- **연장 요청 처리 큐** — 승인 시 `customer_use_deadline` 연장 (CMI 365일 초과 불가)
- **고지 이행 로그** — 동의 시각, 안내 발송 이력. 분쟁 시 근거

> **연장 상한** — `ordered_at + 365일`을 넘길 수 없습니다. 그 이후에는 CMI에서도 회수가 불가하므로 **연장 승인 시 반드시 상한 검증**을 겁니다.

#### (c) 환불 정책 매트릭스 (초안 — 법무 검토 필요)

| 시점 | 고객 환불 | CMI 회수 | 우리 손익 |
|---|---|---|---|
| 결제 후 · CMI 주문 전 | **100%** | 해당 없음 | 0 (PG 수수료만) |
| **주문 후 · 미활성 · 365일 이내** | **100%** | **100% 롤백** | **0** (PG 수수료만) |
| **현지 활성화 후** | **불가**(원칙) | 불가 | — |
| **180일 미사용 자동소멸**(자체 규정) | 불가 | **취소로 100% 회수** | **소매가 전액 순이익** |
| 365일 초과(연장 승인 오류 등) | 불가 | **불가** | **원가 전액 손실** — 연장 상한 검증 필수 |
| **CMI 주문 실패** | **100% 자동취소** | 원가 미발생 | 0 |
| 기기 비호환 · 망 접속 불가 | **100%**(귀책 확인 시) | 미개통이면 가능 | 상황별 |

> **자체 규정 180일을 적용하면 원가 손실 구간이 사라집니다.** 180일 시점에 공급사 취소로 원가를 회수하고, 고객 결제분은 소멸 수익으로 남습니다.
> **유일한 사고 지점은 「CMI 365일을 넘겨버리는 것」**입니다. 만료 배치가 밀리거나 연장을 과도하게 승인하면 회수가 막힙니다.
> → 어드민 대시보드에 **미활성 잔액**(아직 안 쓴 주문의 원가 합계)과 **365일 임박 건수**를 상시 표시합니다.

#### (d) 법적 근거 — 전자상거래법 (법무 검토 전제)

- **청약철회 기간 7일**이 원칙입니다.
- 다만 **디지털콘텐츠의 제공이 개시된 경우 철회가 제한**될 수 있습니다. eSIM에서 "제공 개시"를 **QR 발급 시점**으로 볼지 **개통 시점**으로 볼지가 쟁점입니다.
- 제한하려면 **구매 전에 그 사실을 명확히 고지하고 동의**를 받아야 합니다. 고지 없이 제한하면 무효가 될 수 있습니다.
- **가분적 콘텐츠**는 미제공 부분에 대한 철회가 가능하다는 점도 검토 대상입니다.

> **결론적으로 "구매 화면에서의 사전 고지 + 동의 체크"가 규정의 실효성을 좌우합니다.** 결제 단계 UI에 반드시 포함해야 합니다.

  → [미활성 & 365일 내]  3.2.12 채널 해지 (성공코드 0000000)
                        or 3.2.9 조기 종료

```

> **환불 직전 재조회는 생략하면 안 됩니다.** 웹훅(`3.2.15`)을 놓친 사이 고객이 현지에서 활성화했다면, 우리는 미활성으로 알고 환불해주지만 **CMI에서는 회수가 안 됩니다.** 고객 돈은 나가고 원가는 못 건지는 최악의 조합입니다.
> → 환불 API 진입 시 **반드시 `3.2.6`으로 현재 상태를 다시 확인**한 뒤 판정합니다.

**부분 실패 처리** — `3.2.9`는 다건 요청 시 `errorList`로 실패 건만 개별 반환합니다. **일부만 성공한 상태를 화면에 그대로 보여주고 재시도**할 수 있어야 합니다.

**성공코드 주의** — `3.2.12`는 **`0000000`**, 나머지는 대부분 **`0`**입니다. 어댑터에서 인터페이스별로 판정을 다르게 해야 합니다.

#### (f) 어드민 화면

**환불 관리**
- 요청 목록 — 상태(대기/처리중/완료/거절) · 사유 · **CMI 회수 가능 여부 자동 판정**
- 건별 상세 — 주문 생애주기 타임라인(결제→발급→설치→개통), 각 시점 근거 웹훅 로그
- **일괄 처리** — 주문 실패 건 자동취소 대기열
- **손실 집계** — CMI 회수 불가로 우리가 떠안은 금액. 월별·사유별

**정합성 점검(중요)**
PG 취소와 CMI 해지가 **따로 노는 상태**를 잡아야 합니다.

| 이상 상태 | 의미 |
|---|---|
| PG 취소됨 · CMI 미해지 | **원가만 나감** — 손실 |
| PG 미취소 · CMI 해지됨 | **고객 돈 안 돌려줌** — 분쟁 |
| 양쪽 실패 · 상태만 환불 | 데이터 오류 |

→ **일일 대사(reconciliation) 배치**로 불일치를 뽑아 어드민에 띄웁니다.

> **API에 환불 금액 정산 개념이 없습니다.** 해지는 CMI 선불 잔액으로 돌아오므로, **PG 환불과 CMI 해지를 별도 트랜잭션으로 짝지어 관리**해야 합니다.

#### (g) ★멀티 공급사 환불 — 조건이 공급사마다 다르다

**최저가 자동 라우팅과 환불규정이 정면으로 충돌합니다.**

```
같은 "일본 1GB 3일"을
  고객A → CMI로 발급      → 미활성이면 365일 내 100% 회수
  고객B → A2Z 거래처 발급  → 취소 수수료가 붙을 수 있음
```

**같은 상품을 산 두 고객의 환불 조건이 달라집니다.** 고객에게는 **단일 규정**만 제시할 수 있으므로 그대로 두면 안 됩니다.

> A2Z 거래처는 근본 규칙이 CMI와 같아 **차이는 크지 않을 전망**이지만, **수수료·기한 단축이 하나라도 있으면 교집합이 그쪽으로 내려갑니다.** 계약 전에 반드시 확인해야 하는 이유입니다.

##### 원칙 1 — 고객 규정 = 전 공급사 조건의 **교집합**

가장 제약이 큰 공급사에 맞춰 고객 약관을 씁니다. 그보다 관대한 공급사에서 생기는 여유는 **우리 이익**으로 남습니다.

| 항목 | CMI | 공급사B | **고객 고지값** |
|---|---|---|---|
| 취소 가능 조건 | 미활성 | 미활성 | 미활성 |
| 취소 기한 | 365일 | (예) 90일 | **90일** ← 짧은 쪽 |
| 회수율 | 100% | (예) 90% | **100% 환불** (차액 10%는 우리 부담) |
| 부분 사용 후 | 불가 | 불가 | 불가 |

##### 원칙 2 — 우리 약속을 못 지키는 공급사는 라우팅에서 배제하거나 비용을 얹는다

**환불 불가 공급사는 겉보기 원가가 싸도 실질 원가가 더 비쌉니다.**

```
실질원가 = 공급단가 + (미회수 위험액 × 예상 환불률)

CMI      2,622 + (0 × 5%)      = 2,622원   ← 미활성 100% 회수
공급사B   2,410 + (2,410 × 5%)  = 2,531원   ← 환불 시 회수 불가
```

→ **라우팅 비교값은 공급단가가 아니라 실질원가**입니다. `esim_sku_supply.effective_cost`로 계산해 정렬합니다. 예상 환불률은 **공급사별 실적에서 자동 갱신**합니다.

##### 공급사 환불조건 정규화 모델

공급사마다 표현이 다르므로 **공통 스키마로 정규화**해 저장합니다.

```
supplier_refund_terms(
  supplier_id,
  cancelable_states[],        -- 어느 상태에서 취소 가능 (ordered / installed …)
  cancel_window_days,         -- 주문 후 취소 가능 기한 (CMI 365 / A2Z 180 예상)
  recovery_rate,              -- 회수율 (1.0 = 전액)
  partial_refund bool,        -- 부분 사용 후 부분환불 지원
  cancel_fee_krw,             -- 취소 수수료
  settlement_lag_days,        -- 환불금 반영까지 소요일
  proof_required,             -- 증빙 요구 여부
  verified_at, source         -- 계약서/구두/API 중 무엇으로 확인했는지
)
```

> **`source`가 중요합니다.** 구두 확인만 있는 조건은 분쟁 시 근거가 없습니다. **계약서 조항이나 서면 답변으로 확정된 것만 `verified`**로 표시하고, 미확인 공급사는 **보수적으로 최악값**을 적용합니다.

> **A2Z 거래처의 경우** — 근본 규칙(미활성 취소·365일)은 CMI와 같을 가능성이 높지만, **거래처가 덧씌운 조건이 있는지**를 계약서로 확인해야 합니다. 특히 `cancel_fee_krw`(취소 수수료)와 `cancel_window_days`(기한 단축), `settlement_lag_days`(환불금 반영 지연) 세 가지입니다.

##### 운영

- 주문에 기록된 **라우팅 결과(공급사)**로 해지 대상 결정 — 어댑터 `cancel(order)`가 공급사별 제약을 캡슐화
- `capabilities.supportsEarlyEnd` / `supportsPartialRefund`로 화면 액션 노출 제어
- **공급사별 환불 실적 대시보드** — 요청 건수·성공률·평균 회수율·미회수 손실액
- 이 데이터가 **다음 계약 협상의 근거**이자 **실질원가 산식의 입력값**입니다

### 2.9 실명제 대상 관리 (P2)

`3.2.10`의 `realRuleList`가 비어 있지 않은 목적지는 **신분증 인증이 필요**합니다.

client/src/pages/admin/esim/    어드민 화면
```

**어댑터에서 반드시 처리할 것**

| # | 항목 |
|---|---|
| 1 | **WSSE** — `Base64(SHA256(Nonce + Created + Password))`, `Created`는 UTC, 10분 유효 |
| 2 | **토큰 캐시** — 10분 만료, 만료 전 갱신 |
| 3 | **UTC ↔ KST 변환** — 전 시각 필드가 UTC0. 9시간 보정 |
| 4 | **성공코드 분기** — 대부분 `0`, 3.2.12는 `0000000` |
| 5 | **`is_Refuel` 반전 주의** — `0`이 추가충전 |
| 6 | **`429` 대응** — 호출 빈도 제어·백오프 |
| 7 | **선택 필드 규칙** — 숫자형은 빈 값으로 보내면 안 되고, 객체형은 노드 자체를 생략 |
| 8 | **★멱등키(Idempotency Key) 필수** — `transactionCode`(3.2.5, 32자)를 우리 주문번호 기반으로 생성. **중복 주문 = 중복 차감**이므로 재시도 시 반드시 같은 값 사용 |
| 9 | **CMI 응답 원문 + Request ID 감사로그 저장** — 분쟁·대사의 유일한 근거 |
| 10 | **Balance 부족 시 주문 전 차단** — 잔액 조회 후 진행. 부족하면 운영자 알림 |

## 7. 미해결 리스크

- **발급 실패 = 돈은 받고 상품 없음.** 결제 자동취소가 1순위 안전장치
- **선불 잔액 소진 시 구독 즉시 정지** — 잔액 경보가 곧 서비스 중단 방지
- **CMI가 패키지를 임의 단종**(8/17 70건). 동기화 시 자동 진열 중단 필수
- **가격표 분기 갱신** — 계약서상 quarterly. 소매가를 미리 걸어두는 구조와 충돌
- **덤핑 판정이 CMI 재량** — 최저가 지정은 현재 없으나, "시장 교란" 판단은 CMI가 합니다. 경쟁사 대비 극단적 저가 정책은 피하는 게 안전
