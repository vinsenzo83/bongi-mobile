> 데스크(봇·상담사)가 **남의 스키마인 `cs`** 와 사내 상품 테이블을 어떻게 쓸 것인가

> 짝 문서: `docs/specs/cs-chat-desk-2026-09-03.md`(데스크 PRD) · 시드: `server/db/desk-standalone/008-canned-replies-seed.sql`

## 0. 한 줄 결론

**C(주기 동기화) 를 권고한다.** 원본은 `cs` 에 두고, 데스크는 `desk.kb_*` 사본을 갖는다.
여기에 **A 의 최소 부분 — 답변 시점 값 스냅샷** 을 더한다. 봇이 인용한 근거는 id 가 아니라 **그때의 값** 으로 남겨야 사후 검증이 된다.

B(실시간 조회)는 채택하지 않는다. `cs` 가 죽으면 봇도 상담사도 같이 죽는다.
A(통째 복사, 사본만 보유)도 채택하지 않는다. 요금제는 개편이 잦아 사본이 곧 틀린 답이 된다.

### 1.2 설계를 바꾸는 실측 4가지

1. **`cs` 는 이미 2개월 낡았다.** 모든 크롤 테이블의 `crawled_at` 최댓값이 **2026-07-05**, `cs.crawl_meta` 마지막 갱신도 2026-07-05(LG U+ vas 1행뿐). 즉 "크롤러가 계속 갱신한다"는 전제가 **dev 에서는 현재 성립하지 않는다.** 신선도는 설계가 아니라 **운영 문제**이고, 어느 안을 골라도 별도로 고쳐야 한다.
2. **의미검색이 지금은 불가능하다.** `cs.faqs.embedding` · `cs.plans.embedding` 컬럼은 있으나 **채워진 행 0건**. PRD §B1 "의미검색 점수 임계값 미달 시 인계"는 현재 코드로 실행할 수 없다.
3. **통신사별 지식 편중.** `cs.faqs` 는 SKT 201 · LG U+ 59 · KT 42 · 공통 6. 봇 답변 품질이 통신사에 따라 크게 달라진다.
4. **데스크는 `cs` 를 아직 한 줄도 읽지 않는다.** `server/` 전체에 `cs.faqs`/`cs.plans`/`cs.carrier_links` 참조 0건. 배선이 통째로 비어 있으므로, 지금이 방식을 고르기에 정확한 시점이다.

## 2. 데스크가 자료에 요구하는 것 (판단 기준)

| # | 요구 | 이유 |
|---|---|---|
| R1 | **가용성** — `cs` 가 죽어도 봇·상담사는 답한다 | 상담은 실시간이다. 저쪽 장애가 우리 응대 중단이 되면 안 된다 |
| R2 | **신선도** — 요금제 개편이 반영된다 | 틀린 요금을 자신 있게 답하는 것이 최악. 상용구에서 가격을 뺀 이유와 같다 |

### 결론

**C + (A 의 스냅샷 부분)**.
근거는 세 줄이다.
- R1 을 포기할 수 없다 → B 탈락. 데스크의 기존 원칙("저쪽이 죽어도 우리 상담은 계속된다")과 정면으로 어긋난다.
- R2 를 포기할 수 없다 → A 탈락. 요금제는 개편이 잦다는 것이 이 프로젝트의 전제다.
- R3 은 A·B·C 어느 것도 자동으로 주지 않는다 → **인용 시 값 스냅샷**을 별도로 설계한다(§5).

## 4. 동기화 설계 (구현 대상 아님 — 배선도)

### 4.1 방향과 경계

```
[cs 스키마 · 남의 소유]                    [desk · 우리 소유]
  faqs/plans/vas/wired/bundles/links
        │  ① public.cs_kb_pull(...)  SECURITY DEFINER · SELECT 전용
        ▼
   sync worker (server/services/desk-kb-sync.js)   ── 크론
        │  ② upsert (natural key 기준)
        ▼
   desk.kb_faqs / kb_plans / kb_vas / kb_wired / kb_bundles / kb_links
   desk.kb_sync_log  (배치별 성공·행수·해시)
        │  ③ 조회는 사본만
        ▼
   봇(근거 검색) · 상담사 UI(/찾기) · 상용구 링크
```

- **`cs` 에는 SELECT 만 한다.** 쓰기 경로를 아예 만들지 않는다(R5).
- `cs` 는 PostgREST 노출 대상이 아닐 수 있으므로, 데스크가 자기 스키마에 쓰는 방식과 동일하게 **`public` SECURITY DEFINER 읽기 함수** 하나를 게이트웨이로 둔다. 프로젝트가 분리되면 이 함수만 HTTP 호출로 바뀌고 워커 로직은 그대로다(R4).
- **id 를 신뢰하지 않는다.** `cs` 는 staging 승격 구조라 id 안정성이 보장되지 않는다. 사본은 자연키로 맞춘다.

| 사본 테이블 | 자연키(upsert 기준) |
|---|---|
| `kb_faqs` | `(carrier, topic_code, question)` |
| `kb_plans` | `(carrier, plan_name)` |
| `kb_vas` | `(carrier, category, name)` |
| `kb_wired` | `(carrier, category, name)` |
| `kb_bundles` | `(carrier, bundle_name)` |
| `kb_links` | `(carrier, kind)` |

공통 컬럼: 원본 값 + `src_id`(참고용) · `src_crawled_at` · `synced_at` · `row_hash` · `is_active` · `retired_at`.

### 4.2 주기

| 테이블 | 주기 | 근거 |
|---|---|---|
| `kb_plans` | **6시간** | 개편이 가장 잦고 금액을 직접 인용한다. 틀리면 피해가 가장 크다 |
| `kb_wired` · `kb_bundles` | **12시간** | 인터넷·결합도 금액을 말한다. 변동은 요금제보다 느리다 |
| `kb_vas` | **24시간** | 573건으로 양이 많고 변동은 완만 |
| `kb_faqs` | **24시간** | 절차 설명 위주 → 변동 느림. 단 임베딩 재생성이 붙으면 비용이 여기서 난다(§7) |
| `kb_links` | **24시간** | 27건. 그러나 **URL 이 죽으면 고객이 막힌다** → 별도 링크 헬스체크(주 1회, HEAD)를 같이 돈다 |

전부 **전량 비교 upsert**(행수가 최대 573건이라 증분 로직이 이득이 없다). `row_hash` 가 같으면 UPDATE 를 건너뛰어 `synced_at` 만 갱신한다.

**삭제 처리**: 원본에서 사라진 행은 **지우지 않고** `is_active=false` + `retired_at` 을 찍는다. 과거 대화의 근거 참조가 끊기면 안 된다(R3).

### 4.3 실패 시 정책 (★ 여기가 이 설계의 핵심)

| 상황 | 동작 |
|---|---|
| `cs` 조회 실패 (1회) | 지수 백오프 재시도 3회. **사본은 그대로 둔다** — 마지막 성공본으로 계속 답한다(R1) |
| 3회 연속 실패 | `kb_sync_log` 에 `failed` 기록 + 텔레그램 임원방 알림. 사본 유지 |
| 원본 행수가 직전 대비 **50% 이상 급감** | **승격하지 않는다.** 크롤 실패로 빈 배치가 올라오는 상황과 구분이 안 되므로 사본을 지키는 쪽을 택한다. `blocked` 로 기록 + 알림 |
| 사본 신선도 초과 (§4.4) | 봇: 해당 영역 **답변 금지 → 인계**. 상담사 UI: 근거 카드에 "N일 전 자료" 배지 |
| 링크 헬스체크 실패 | 해당 `kb_links` 행 `is_active=false`. 상용구가 그 링크를 쓰면 관리자 알림 |

**실패 사유를 버리지 않는다.** `kb_sync_log` 에 배치별 `ok/failed/blocked` · 사유 원문 · 행수 스냅샷을 남긴다. 사유를 지우면 왜 멈췄는지 영원히 모른다.

### 4.4 신선도 계측 (동기화보다 중요하다)

동기화의 진짜 실패는 에러가 아니라 **조용한 정지**다. §1.2 의 "2개월 낡음"이 정확히 그 상태다.

| 테이블 | `stale` 임계 | 초과 시 |
|---|---|---|
| `kb_plans` | 48시간 | 봇이 금액을 말하지 않는다 → "확인 후 안내" + 인계 |
| `kb_wired`·`kb_bundles` | 72시간 | 〃 |
| `kb_vas`·`kb_faqs` | 7일 | 답하되 상담사 화면에 배지 |
| `kb_links` | 30일 | 배지만 (링크는 잘 안 바뀐다) |

- 노출: `public.desk_kb_health()` → 테이블별 `last_ok` · `age` · `rows` · `state(fresh|stale|blocked)`.
- 데스크 관리자 화면 한 줄, 텔레그램 일일점검에 한 줄.
- **`stale` 판정은 사본 나이가 아니라 `src_crawled_at` 나이도 함께 본다.** 동기화가 매시간 성공해도 원본이 두 달 전이면 그 자료는 낡은 것이다. 지금이 그 상태다.

## 5. 답변 근거 스냅샷 (R3 — 어느 안을 골라도 별도로 필요)

현재 PRD 형식은 `bot_sources: ["cs.faqs#183"]`. **id 만으로는 사후 검증이 안 된다.** 크롤러가 183번 행을 덮어쓰면, 봇이 무엇을 보고 답했는지 영원히 알 수 없다.

제안 형식 (`desk.messages.bot_sources`):

```json
[{
  "ref": "kb_plans#412",
  "src": "cs.plans#287",
  "matched": "5G 슬림+",
  "value": { "monthly_fee": 55000, "data_amount": "11GB+매일2GB" },
  "src_crawled_at": "2026-07-05T06:13:42Z",
  "synced_at": "2026-09-04T03:00:00Z",
  "score": 0.83
}]
```

- `value` 는 **답변에 실제로 인용한 필드만** 담는다(행 전체 복사 금지 — 메시지가 비대해진다).
- `src_crawled_at` 이 함께 남아야 "그때 우리가 가진 자료가 두 달 전 것이었다"는 사실이 사후에 드러난다.
- 상담사 UI 는 이 값을 근거 카드로 그대로 보여준다(PRD §498 그대로, 값이 추가될 뿐).

## 6. 상용구와의 관계

`008-canned-replies-seed.sql` 의 상용구 47건은 **가격·기간·조건을 본문에 넣지 않았다.** 대신 `{{변수}}` 또는 "확인 후 안내"로 두었다. 이유가 이 문서의 R2 와 같다 — 상용구는 사람이 손으로 고치기 전까지 영원히 그대로이므로, 변하는 값을 담으면 틀린 정보를 굳힌다.

**예외는 `cs.carrier_links` 의 3사 조회링크·대표번호**다. 이것만 본문에 박았다.
실측: 상용구 12건에 URL **17종(20회)** 이 들어갔고, **전부 `cs.carrier_links.url` 과 문자열 일치**한다(지어낸 링크 0건). 대표번호(114·100·101·1599-0011·1544-0010·1335)도 같은 테이블 `phone` 값을 옮긴 것이다. 이유:
- 개인 실시간값(내 요금·내 위약금·내 개통 상황)은 **우리가 조회할 수 없다.** 링크를 주는 것이 유일하게 정확한 응대다.
- 대표번호(114·100·101·1335)와 조회 URL 은 변동이 드물다.

**대신 부채가 생긴다**: 링크가 상용구 본문에 복사되어 있으므로, 원본이 바뀌면 상용구도 손으로 고쳐야 한다. 해소 방안 두 가지 — 결정 필요:

| 안 | 내용 | 평가 |
|---|---|---|
| ㄱ | 상용구 본문에 `{{링크:KT:bill_check}}` 같은 **자료 참조 토큰**을 두고, 삽입 시점에 `kb_links` 에서 치환 | 근본 해결. 렌더러 1개 필요 |
| ㄴ | 현행 유지 + §4.3 링크 헬스체크가 깨진 링크를 알려주면 손으로 수정 | 지금 상태. 구현 0, 사람이 반응해야 함 |

**권고 ㄱ.** 상용구 삽입은 이미 `{{변수}}` 치환을 하므로 토큰 하나가 더 늘 뿐이다.

## 8. 하지 않기로 한 것

- `cs` 에 쓰기 (컬럼 추가·플래그 갱신 포함) — 소유가 다르다.
- `cs.*` 직접 조인으로 봇 답변 조립 — 분리 시점에 전부 다시 짜야 한다.
- 사본에서 원본 행 **삭제** — 과거 대화의 근거가 끊긴다. `is_active=false` 로만 처리.
- 상용구 본문에 금액·기간·조건 박기 — 틀린 정보를 굳힌다.
